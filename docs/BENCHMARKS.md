## 2026-08-24: 二段パス補正 (改善イテレーション#10)

- 事前実験: VAD分割セグメントをギャップ2秒未満で結合して一括再デコードすると CER **15.5%→12.0%**（実放送ja、23%相対改善）。
- 実装: 発話群が2秒の無音で閉じたら（発話中は閉じない）、履歴バッファから群全体+プリロールを取り出して一括再デコード。
  結果は `[refine/lang]` 行・SSE `refine` イベント・`--transcript` ファイルに出力。速報の確定字幕はそのまま。
- 防御: refine結果が速報合計の70%未満の長さなら内容喪失とみなし速報版を採用（rzのTTS癖で実際に発動を確認）。
- 副次効果: 結合デコードにより文脈が増え、単独では欠けた語頭（「明日の」）が refine で復元されるケースを確認。
- 群の上限25秒（30秒の履歴バッファ内に収める）。`--no-refine` で無効化可。

|---|---|---|
| ja | 8.6% | 9.9% |
| en | 9.4% | 10.2% |
| ko | 8.1% | 9.1% |

jaの内訳は改善16クリップ・悪化26クリップ。悪化の主因は2つ:
- 分割境界にまたがる語が消える（`ja_01974_00245` の「ズボンを履くことが」が丸ごと欠落）。
- 断片が誤った言語のモデルに流れる（`ja_01813_00506`）。バッファ単位で決めたはずの言語が
  断片デコードの結果で覆るリークがあった（下記）。

**言語リークの原因**: `transcribe()` は decode の後に `script_corrected_lang(lang, text)` で
「文字種がLIDタグと矛盾していないか」を見て、矛盾していればモデルを変えて再デコードする。
この `text` が分割後の結合テキストになっていたため、分割で崩れた出力（ラテン文字混じり等）が
そのまま言語判定を動かし、ja のクリップが en モデルに回されていた。**言語決定の入力に
分割結果が混ざっていたことがリーク本体**で、断片ごとのLIDを書いていないことは防御にならない。

**やり直した設計**: 分割はデコード経路ではなく**再試行**にした。
1. まず今まで通りバッファ全体を1回デコードする（疑わしくないバッファの出力は
   分割機能導入前とバイト単位で同一）。
2. その出力が「話した長さのわりに文字数が少なすぎる」ときだけ疑う。
   しきい値は FLEURS ja test を本番経路（rz tier）に通して実測した:
   健全な60クリップは**発話秒あたり 3.46〜14.22文字**（中央値6.54）、
   head-dropout の clip 15 は **1.70文字/秒**。その対数中点 **2.4文字/秒**を採用した
   （欠陥より41%上、健全側の最小より31%下）。分母は「バッファ長」ではなく
   「VADが speech と判定した秒数」——バッファに含まれる無音の量は切り方の事情でしかなく、
   FLEURSクリップとライブVADセグメントで同じ欠陥が同じ見え方をしないと使えないため。
   speech ≤ buffer なのでバッファ長で割った値は必ず小さく出る。これを
   「VADを回す価値があるか」の無料の前段ゲートに使っている（見落としは原理的に出ない）。
3. 再試行は0.35秒以上の内部無音で分割し、**バッファ全体のデコードを出したその認識器に
   固定**して各ピースをデコードする。断片ごとのLIDも文字種補正もomniフォールバックもしない
   （空で返ったピースは空のまま落とす）。前後の実音コンテキストは0.15秒→**0.35秒**に拡大した。
4. 採用条件は「長くなり」かつ「密度が正常域に戻り」かつ「全体デコードの末尾が再試行結果の
   中に残っている」こと。全体デコードは*生き残った末尾*なので、本物の復元なら末尾は保たれる。
   曖昧なときは全体デコードを残す。

**ローカル検証**（Windows, minimal install: rz/whisper-tiny/vad/punct のみ）:
FLEURS ja test から head-dropout 2本・外部が名指しした回帰2本・ランダム10本を取った
ミニセットで、変化したのは clip 15 のみ（**CER 0.667 → 0.111**）。
`ja_01974_00245` `ja_01813_00506` を含む残り13本はバイト単位で不変。
別途ランダム120クリップでも**変化0件**（平均CER 0.0606で前後一致、実時間も同等）。
en/ko はモデルが手元に無く経路が成立しないため、ローカル値には意味がない。
ラテン言語のしきい値 6.0文字/秒は CJK 実測値の2.5倍という文字数比からの外挿で、
フルスコアカードでの確認が必要。

## 2026-09-01: ライブ経路の発話冒頭欠け疑いを実測 — 既存のVADプリロールで防げていた

**発端**: 上記 head-dropout 調査（`8d474fc`）の副産物として、ライブ経路にも同型の疑いが
挙がった。Silero VAD の発話開始検出は実際の発話開始より遅れることがあり、もし VAD セグメント
（`vad.front.samples`）を検出開始点からそのままデコードしていれば、発話の最初の単語が
欠ける・化けるはず、という筋である。オフライン分割側は各断片の前後に実音コンテキストを
足すことで解決済みだったが、ライブ経路では実際に起きるのか未検証だった。

**検証方法**: `testdata/multi_sentence_ja.wav`（edge-tts 合成、無音助走なしで発話が
立ち上がる3文、間隔0.5秒 — tests/test_asr_segment.py のフィクスチャ）を、本番のライブ構成
そのもの（`build_vad()` + `AudioHistory` + `drain_segments()`、rz tier・ja固定）に通し、
(a) VAD の検出開始点と真のエネルギー立ち上がりのずれ、(b) 現行プリロールあり／なしの
デコード結果、を比べた。

**結果**:
- 検出遅れは実在する。立ち上がりの速い第1文で VAD は真の開始より **198ms 遅れて**
  発話開始を切った（第2・3文は ±25ms 以内）。
- プリロールを 0 にする（＝疑われた「front.samples をそのまま使う」挙動）と、頭は実際に
  壊れた: 第3文「資料は昨日送りました」が「**昨日**は昨日送りました」になった。遅れが
  18ms しかないセグメントでも冒頭語が化けており、欠けの深刻さは遅れ量に単調ではない。
- ただし現行コードは既に `AudioHistory.with_preroll()`（`PREROLL_S=1.0`、`20c16d6` で
  導入）が `drain_segments()` で VAD セグメントの前に履歴から最大1秒の実音声を前置して
  おり、この経路では **3文とも冒頭語が残った**（「東京の天気は晴れです」「あしたの会議は
  十時からです」「資料は昨日送りました」）。プリロールは直前セグメント末尾でクランプ
  されるので前の発話への食い込みも起きない（tests/test_units.py の AudioHistory 群）。

**判断**: ライブ経路への追加修正は不要。疑い自体は正しかった（プリロールが無ければ
実害が出る）ので、この不変条件を tests/test_asr_segment.py の
`test_live_path_preroll_keeps_utterance_initial_words` で固定した: フィクスチャ3文を
VAD → プリロール → デコードの実経路に通し、各文の冒頭語（仮名表記も正: 「明日」は
「あした」と出るのが正常で欠落ではない）が全て残ることを要求する。モデル未配置の環境では
既存の needs_models 規約でスキップされる。
## 2026-09-01: FLEURS test 5言語×100本 統一head-to-head (v0.3.1 リリースチャート用)

これまでの `docs/SCORECARD.md`（real-speechセット、言語あたり12〜15本）や
`docs/EVAL_REAL_ZHKO.md` / `docs/EVAL_REAL_YUE.md`（別々のセット・別々の日付で計測）を
一本化し、**同一クリップ・同一採点・同一CPU**で hayamimi 本番経路 と
faster-whisper large-v3-turbo を5言語×100本、直接比較した。

### データ

- [google/fleurs](https://huggingface.co/datasets/google/fleurs) **test** split。
  `datasets-server` の `/rows` API は本データセットで HTTP 500 を返すため、
  HF の parquet 自動変換ルート
  (`https://huggingface.co/api/datasets/google/fleurs/parquet/<config>/test/0.parquet`)
  を `fsspec` + `pyarrow` で直接読む方式に切り替えた
  (`scripts/make_fleursset.py`)。5言語とも1シャード (`0.parquet`, 382〜945行) に収まった。
- 設定: `ja_jp` / `en_us` / `cmn_hans_cn` / `ko_kr` / `yue_hant_hk`。
- 選定規則: 各言語のparquetテーブルを **FLEURS `id` フィールドで安定ソート**し
  （同一idが複数recording/speakerに紐づき数件重複するが、同順位はparquet内の元の行順で解決）、
  先頭から空文字起こし・デコード失敗・非16kHzをスキップしつつ **先頭100本**を採用。
  埋め込み音声はすでに16kHzモノラルのため再サンプリングなし。
  除外クリップ: **0件**（5言語とも100/100本を初回取得で確保、デコード失敗なし）。
- 出力: `testdata/fleurs_bench/<lang>/manifest.json` + `<lang>_NNN.wav`（gitではtestdata配下は非追跡）。

### 採点条件

- `scripts/eval_fleurs_bench.py`。en=WER（jiwer）、他=CER（Levenshtein、NFKC正規化＋
  句読点/空白除去、`scripts/eval_accuracy.py` の `wer_en`/`cer_ja` をそのまま再利用）。
  yueはopencc t2s正規化後に比較（既存スコアカードと同じ規約）。
- **hayamimi**: `asr_engine.RoutedASR(threads=6, preload=False)`、`scripts/eval_engine.py` と
  同じ本番経路（whisper-tiny LID自動判定 → tier振り分け → デコード → ja句読点）。
  second-opinion は既定値のOFF（`ja_second_opinion=False`）。言語ブロックごとに
  `reset_session()` を1回呼び、sticky-LIDのヒステリシスが前言語の残響を持ち込まないようにした

- **turbo**: `faster-whisper` `large-v3-turbo`、`device=cpu`、`compute_type=int8`、

  やや有利な非対称条件 — `docs/COMPARISON.md` に記載済みの規約と同じ）。
- CPU: Ryzen 5 5600 (6C12T, 6スレッド指定) / Windows 11。sherpa-onnx 1.13.6、

### 制約

- **turboに正解言語を渡す非対称条件**（`docs/COMPARISON.md`と同じ規約）。hayamimiは
  LIDも含めた完全自動判定でこの数字を出している一方、turboはlanguage引数で正解を
  与えられているため、turbo側の精度はやや有利な条件での測定値。
- **second-opinion OFF**。本番のオプション機能（ja再デコードの合意ゲート）は既定値のまま
  無効にして測定した。有効化した場合のja精度は本表に含まれない。
- **FLEURSはread-aloudの単一話者クリップ**であり、雑音・オーバーラップ・自然発話ではない。
  実運用条件（マイク入力・雑音・話者交代）ではここでの差がそのまま出るとは限らない。
- **結果JSONは非追跡**（`testdata/fleurs_bench/results_{hayamimi,turbo}.json`）。再現する場合は
  `scripts/make_fleursset.py --lang all` → `scripts/eval_fleurs_bench.py --engine ... --lang ...`
  を参照。
